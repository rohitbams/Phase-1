Tier Descriptions

Klasher (Standard)

Visual Identifier: KO Blue box

Target User: Music enthusiasts, casual competitors, social users

Core Features

  • Create and manage user profile
  • Organize klashes with up to 50 participants
  • Spectate, join, and compete in klashes
  • Access all music genres in real-time
  • 30/60/90 second klash durations
  • Create and share playlists
  • Follow other users
  • Live messaging
  • Join KO-organised klashes
  • Go Live feature

Klash Coin Restrictions

  • To Earn: Minimum 1,000 followers AND 1,000 wins required
  • To Gift: Minimum 1,000 followers AND 1,000 wins required
  • To Spend: Can purchase and spend coins without threshold

Limitations

  • Cannot upload own music
  • Cannot host unlimited-participant klashes
  • Cannot earn hosting fees
  • Cannot set entry stakes
  • Must invite at least 1 friend to commence klashing

Independent Klasher

Visual Identifier: Purple box (or half purple/half blue if also Klasher)

Target User: Independent artists, music creators, promotional users

All Klasher Features PLUS:

  • Music Upload: Upload and promote own music (3 tracks maximum at one time)
  • Top 40 Klash Charts: Eligible for independent music charts
  • Klash Own Music: Compete using uploaded tracks
  • No Coin Threshold: Gift and receive Klash Coins immediately (no follower/win requirement)
  • Unit Revenue: Earn from music sales/streams
  • Go Live Showcase: Paid performance feature for showcasing talent

Upload Constraints

  • Maximum 3 songs/tracks uploaded at one time (server load management)
  • 90-day retention period (tracks reviewed based on plays, downloads, coins gifted, klashes, likes)
  • Monthly analytics report provided
  • Supported formats: TBD with Lincoln (see Q3.1)

Super Klasher

Visual Identifier: Indigo box

Target User: Event hosts, influencers, professional klashers

All Klasher Features PLUS:

  • Unlimited Participants: Host klashes with no participant cap
  • Set Entry Stakes: Define joining fees for each hosted klash
  • Host Revenue: Receive percentage of every klash organized
  • No Coin Threshold: Gift and receive Klash Coins immediately
  • Go Live: Access to live streaming features

Revenue Model

Source: Coin Wallet Document (27 May 2026)

  • Super Klasher receives a percentage of the hosting fee
  • Super Klasher receives a percentage of the winnings
  • Entry fees deposited into escrow pot → distributed to 1st/2nd/3rd place + host fee
  • Exact percentages: UNDEFINED — see Q8.3

App Store In-App Purchase Compliance

Source: Requirements Document (Domain Requirement D03)

⚠️ REGULATORY CONSTRAINT
If tiers are sold as in-app purchases on iOS/Android, Apple and Google take 15-30% commission. This significantly impacts the pricing model.

Apple App Store IAP Policy

  • Commission: 30% (first year) → 15% (subsequent years for subscriptions)
  • Small Business Program: 15% for developers earning <$1M/year
  • Requirement: All digital goods/services MUST use Apple IAP (cannot bypass to external payment)

Google Play Store IAP Policy

  • Commission: 30% (standard) → 15% (subscriptions after year 1, or apps <$1M revenue)
  • Requirement: All digital goods/services MUST use Google Play Billing

Impact on KO

If a user purchases a tier upgrade for £10 on iOS:

  • Apple takes £3 (30%) or £1.50 (15%)
  • KO receives £7 or £8.50

Mitigation Strategies (Require Lincoln's Decision):

  • Price tiers higher on mobile to offset commission
  • Encourage web-based tier purchases (no commission)
  • Absorb the cost and accept lower margins on mobile
  • Make tier upgrades achievement-based (free) instead of paid

Data Model Implementation

Reference: Data Model & ERD

Current Design Decision

Tier is an attribute of User, not an entity.

CREATE TABLE users (
  id UUID PRIMARY KEY,
  username VARCHAR(50) UNIQUE NOT NULL,
  tier VARCHAR(20) NOT NULL DEFAULT 'KLASHER',
  CHECK (tier IN ('KLASHER', 'INDEPENDENT', 'SUPER'))
);

Rationale

  • Only 3 fixed tier values with no additional data of their own
  • No need for a separate tiers table
  • Tier-specific features controlled via application logic

If Multiple Tiers Allowed Simultaneously

Would require a junction table:

CREATE TABLE user_tiers (
  user_id UUID REFERENCES users(id),
  tier VARCHAR(20) NOT NULL,
  activated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, tier)
);

Decision Required: Single tier vs multiple tiers per user (see Q1.4)
