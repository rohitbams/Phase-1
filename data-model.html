Data Model & Entity Relationship Diagram

Database Schema & Class Structure | 20 July 2026

Document Purpose

This document provides the complete database schema for KlashOut, including entity definitions, relationships, and implementation guidance for Phase 2.

Two Subdomains

The data model is organized into two logical subdomains:

  • Social / Gaming Core: Users, music, klashes, tournaments, social graph
  • Economy: Wallet, transactions (double-entry ledger)

Note: This schema is based on the 1:1 fiat-backed wallet assumption. If blockchain approach is confirmed (C01), wallet entities will change significantly.

Relationship Summary

From Entity Relationship To Entity Cardinality Implementation
User uploads Track 1:N Track.artist_user_id → User.id
User creates Playlist 1:N Playlist.user_id → User.id
User follows User M:N Junction: Follow (follower_id, following_id)
User has Wallet 1:1 Wallet.user_id → User.id (polymorphic)
User participates in Klash M:N Associative: KlashParticipation (has attributes)
Genre categorizes Track 1:N Track.genre_id → Genre.id
Genre categorizes Klash 1:N Klash.genre_id → Genre.id
Playlist contains Track M:N Junction: PlaylistTrack (playlist_id, track_id, position)
Klash receives Vote 1:N Vote.klash_id → Klash.id
Klash may have Wallet 1:1 Wallet.klash_id → Klash.id (pot escrow)
KlashParticipation selected Track N:1 KlashParticipation.track_id → Track.id
Vote for KlashParticipation N:1 Vote.voted_for_participation_id → KlashParticipation.id
Tournament contains Klash 1:N Klash.tournament_id → Tournament.id (nullable)
Wallet debited/credited via Transaction 1:N Transaction.from_wallet_id, Transaction.to_wallet_id

Economy Entities

▶ wallets table schema 
CREATE TABLE wallets (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  -- Polymorphic: belongs to User OR Klash
  owner_type VARCHAR(20) NOT NULL, -- 'USER' or 'KLASH'
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,
  klash_id UUID REFERENCES klashes(id) ON DELETE CASCADE,

  -- Balance (stored-but-derived for performance)
  -- Recomputed daily from SUM(transactions) for audit
  balance DECIMAL(10,2) NOT NULL DEFAULT 0.00,

  currency VARCHAR(3) NOT NULL DEFAULT 'GBP',

  created_at TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMP NOT NULL DEFAULT NOW(),

  -- Polymorphic constraint: exactly one owner
  CONSTRAINT check_owner CHECK (
    (owner_type = 'USER' AND user_id IS NOT NULL AND klash_id IS NULL) OR
    (owner_type = 'KLASH' AND klash_id IS NOT NULL AND user_id IS NULL)
  ),

  INDEX idx_wallets_user (user_id),
  INDEX idx_wallets_klash (klash_id)
);
▶ transactions table schema 
CREATE TABLE transactions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  -- Transaction type (discriminator)
  -- TOP_UP, GIFT, MUSIC_PURCHASE, KLASH_ENTRY, KLASH_WINNINGS,
  -- HOST_FEE, GO_LIVE, NUDGE_PLAY, CASH_OUT
  type VARCHAR(50) NOT NULL,

  -- Double-entry: from → to
  from_wallet_id UUID REFERENCES wallets(id),
  to_wallet_id UUID REFERENCES wallets(id),

  amount DECIMAL(10,2) NOT NULL,

  -- Status: PENDING, COMPLETED, FAILED, REVERSED
  status VARCHAR(20) NOT NULL DEFAULT 'PENDING',

  -- Context (nullable, depends on type)
  klash_id UUID REFERENCES klashes(id),
  track_id UUID REFERENCES tracks(id),

  -- Flexible metadata (JSONB)
  -- Example: {"stripe_payment_intent_id": "pi_xxx", "payout_method": "bank"}
  metadata JSONB,

  -- Stripe idempotency key (prevent double-crediting)
  idempotency_key VARCHAR(255) UNIQUE,

  created_at TIMESTAMP NOT NULL DEFAULT NOW(),

  -- At least one wallet must be specified
  CONSTRAINT check_from_or_to CHECK (
    from_wallet_id IS NOT NULL OR to_wallet_id IS NOT NULL
  ),

  INDEX idx_transactions_from_wallet (from_wallet_id, created_at DESC),
  INDEX idx_transactions_to_wallet (to_wallet_id, created_at DESC),
  INDEX idx_transactions_type (type),
  INDEX idx_transactions_status (status)
);

Key Modelling Decisions

1. Tier as Attribute (Not Entity)

Decision: User.tier is a VARCHAR ENUM, not a foreign key to a Tiers table.

Rationale: Only 3 fixed values (KLASHER, INDEPENDENT, SUPER) with no data of their own. No need for entity.

Impact: Tier permissions checked via WHERE tier = 'INDEPENDENT' in queries.

2. Genre as Entity (Promoted)

Decision: Genre is a full entity, not an attribute.

Rationale: Referenced by both Track and Klash. Controlled vocabulary seeded at initialization.

Impact: Genre list is centrally managed. Changes propagate to all tracks/klashes.

3. KlashParticipation as Associative Entity

Decision: User ↔ Klash M:N relationship is reified (has its own attributes).

Attributes: role, position, track_id, outcome, decision_stick

Rationale: The relationship itself carries data. Contrast with Follow (pure junction — no attributes).

Impact: Vote references KlashParticipation, not User directly. Winner is identified by winner_participation_id.

4. Transaction as Double-Entry Ledger

Decision: Single Transaction table with two FKs to Wallet (from_wallet_id, to_wallet_id).

Rationale: Ledger is balanced by construction. Every debit has a credit. Satisfies NF06 (ACID, zero unbalanced transactions).

Impact: All transaction types (top-up, gift, purchase, etc.) in one table. Discriminated by type field.

5. Wallet.balance as Stored-But-Derived

Decision: Balance is stored in Wallet table but recomputable from SUM(transactions).

Rationale: Performance (O(1) lookup) vs consistency trade-off.

Implementation:

  • Update balance atomically in same transaction that inserts Transaction record
  • Daily reconciliation job: SELECT SUM(amount) FROM transactions WHERE to_wallet_id = ? GROUP BY to_wallet_id
  • Compare stored balance vs computed balance, alert on drift

6. Super Klash Pot as Escrow Wallet

Decision: Klash pot is a Wallet where owner_type = 'KLASH'.

Rationale: Reuses double-entry machinery. Entry fees flow: User wallet → Klash wallet. Winnings flow: Klash wallet → Winner wallets.

Impact: Wallet entity is polymorphic (belongs to User OR Klash, enforced by CHECK constraint).

Implementation Guidance (ORM / Class Structure)

Why Prisma?

  • Excellent DX (developer experience)

Transaction Atomicity Example

Critical for wallet operations (NF06 requirement):

// Gifting coins: User A → User B (atomic)
async function giftCoins(fromUserId: string, toUserId: string, amount: number) {
  return await prisma.$transaction(async (tx) => {
    // 1. Get wallets
    const fromWallet = await tx.wallet.findUnique({ where: { userId: fromUserId } })
    const toWallet = await tx.wallet.findUnique({ where: { userId: toUserId } })

    if (fromWallet.balance < amount) throw new Error('Insufficient balance')

    // 2. Create transaction record
    const transaction = await tx.transaction.create({
      data: {
        type: 'GIFT',
        fromWalletId: fromWallet.id,
        toWalletId: toWallet.id,
        amount: amount,
        status: 'COMPLETED'
      }
    })

    // 3. Update balances atomically
    await tx.wallet.update({
      where: { id: fromWallet.id },
      data: { balance: { decrement: amount } }
    })

    await tx.wallet.update({
      where: { id: toWallet.id },
      data: { balance: { increment: amount } }
    })

    return transaction
  })
  // If ANY step fails, entire transaction rolls back
}

Polymorphic Association (Wallet)

// Prisma doesn't natively support polymorphic associations
// Workaround: Nullable FKs + CHECK constraint (database-level)

model Wallet {
  id         String   @id @default(uuid())
  ownerType  OwnerType @map("owner_type")
  userId     String?  @map("user_id")
  klashId    String?  @map("klash_id")
  balance    Decimal  @default(0) @db.Decimal(10, 2)

  user       User?    @relation(fields: [userId], references: [id])
  klash      Klash?   @relation(fields: [klashId], references: [id])

  @@map("wallets")
}

enum OwnerType {
  USER
  KLASH
}

// Application-level validation in service:
class WalletService {
  async createWallet(ownerId: string, ownerType: 'USER' | 'KLASH') {
    if (ownerType === 'USER') {
      return prisma.wallet.create({
        data: { ownerType: 'USER', userId: ownerId }
      })
    } else {
      return prisma.wallet.create({
        data: { ownerType: 'KLASH', klashId: ownerId }
      })
    }
  }
}
