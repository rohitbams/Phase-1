DD-001: API-First, Client-Agnostic Backend Architecture

APPROVED | Date: 5 March 2026 | Source: Meeting Minutes 5 March 2026

Decision

KO will be built with an API-first architecture where:

  • All business logic resides server-side in a RESTful API
  • Web and future mobile clients are thin presentation layers consuming the same API
  • No web-specific logic in frontend — all must be portable

Context

Meeting minutes (5 March 2026) revealed:

  • Website built first, app developer hired later
  • Website targets DJs/artists (desktop users)
  • App targets everyday users/spectators (mobile users)

This was buried in meeting notes and not mentioned in BRD — yet it is the most consequential architectural decision in the project.

"App and platform will be have to be sequenced. Rohit will work on the website. An App Developer needs to be hired for the App"

"Two types of Users; website – connoisseurs, artists and DJ's (always use their laptops). App – everyday users and spectators."

— Meeting Minutes, 5 March 2026

Rationale

  • Future app developer can build on existing backend without re-engineering business logic
  • Web and mobile serve different populations but access same data/functionality
  • Enables potential third-party integrations
  • Industry best practice for modern multi-platform applications

Alternatives Considered

Alternative Pros Cons Verdict
Monolithic web app Faster initial development App developer must rebuild everything ❌ Not viable
Backend-for-Frontend (BFF) Optimized per client Duplicated logic, harder to maintain ❌ Over-engineered
API-first Portable, future-proof, clean separation Requires upfront API design discipline ✅ Selected

Consequences

  • ✅ App developer can start work immediately without backend changes
  • ✅ Clean separation of concerns
  • ✅ API can be versioned for backward compatibility
  • ⚠️ Requires upfront API contract design (OpenAPI/Swagger spec)
  • ⚠️ Frontend cannot make direct database queries

Related Decisions: DD-002 (Technology Stack), DD-005 (Authentication)

DD-002: Technology Stack Recommendation

PROPOSED | Date: 20 July 2026

Proposed Stack

Layer Technology Rationale
Backend API Node.js + Express.js JavaScript full-stack; WebSocket support; fast development
Database PostgreSQL ACID-compliant (NF06); strong JSON support; horizontal scaling
Real-Time Socket.io Mature; room-based pub/sub; auto-fallback to polling
Cache Redis In-memory performance; leaderboards; session management
Frontend (Web) React + TypeScript Industry standard; type safety; large talent pool
File Storage AWS S3 Music files; CDN distribution; 99.99% uptime
Payment Stripe Connect FCA-licensed; marketplace payouts

Context

Stack must satisfy:

  • NF03 (10K concurrent users)
  • NF01/NF02 (500ms API response, 200ms real-time events)
  • NF06 (ACID financial transactions)
  • API-first architecture (DD-001)

Alternatives Considered

Backend:

  • Python (Django/Flask): Excellent for data-heavy apps; slightly slower real-time
  • Go: Fastest performance; smaller ecosystem; steeper learning curve
  • Node.js: ✅ Best balance of performance, ecosystem, JavaScript full-stack

Database:

  • MongoDB: Flexible schema; not ACID-compliant (fails NF06)
  • MySQL: ACID-compliant; weaker JSON support
  • PostgreSQL: ✅ ACID + JSON + horizontal scaling

Consequences

  • ✅ JavaScript full-stack reduces context switching
  • ✅ Large talent pool for future hires
  • ✅ Proven stack for real-time applications
  • ⚠️ Node.js requires careful async/await error handling
  • ⚠️ PostgreSQL requires schema migrations

DD-003: Wallet as Internal Double-Entry Ledger

WORKING ASSUMPTION | Date: 20 July 2026

⚠️ MUST CONFIRM WITH LINCOLN — See C01 in Conflict Register

Decision (Working Assumption)

Klash Coin implemented as internal double-entry ledger with 1:1 fiat backing, NOT blockchain/Ethereum.

Data Model

  • Wallet entity (belongs to User or Klash)
  • Transaction entity with two foreign keys to Wallet (debit-from, credit-to)
  • Every transaction debits one wallet, credits another (ACID constraint)
  • Wallet.balance is computed field (SUM of credited - debited transactions)

Context

Direct contradiction in source documents:

  • BRD: "Ethereum system, KO will create its own blockchain"
  • Wallet & Coin UX doc: "1 to 1 fiat rate backed by users"

Rationale for Double-Entry

  1. Wallet & Coin UX doc is more recent and describes fiat-like behavior
  2. 1:1 fiat backing is FCA-compliant — clear regulatory path
  3. Blockchain adds no value — KO Coin not traded externally
  4. Double-entry is gold standard for financial systems (500+ years)
  5. ACID transactions (NF06) trivially satisfied by PostgreSQL

Alternatives Considered

Alternative Pros Cons Verdict
Ethereum Smart Contract Trendy; self-custody Volatile value; gas fees; unclear UK regulation ❌ Incompatible with 1:1 fiat
Custom Blockchain Full control Months of development; no clear benefit ❌ Over-engineered
Double-Entry Ledger ACID-compliant; FCA-compatible; battle-tested Less "innovative" ✅ Selected

Consequences

  • ✅ FCA compliance via e-money regulations
  • ✅ ACID transactions guaranteed (satisfies NF06)
  • ✅ No gas fees, instant transactions
  • ✅ Can partner with Stripe/Mangopay for FCA license
  • ⚠️ Must implement reconciliation checks (daily balance audit)
  • ⚠️ Must handle concurrency correctly (database-level locking)

Related Decisions: DD-004 (FCA Compliance), DD-009 (Transaction Types)

DD-004: FCA Compliance — Partner with Licensed Provider

WORKING ASSUMPTION | Date: 20 July 2026

⚠️ MUST CONFIRM WITH LINCOLN + LEGAL ADVISOR

Recommendation

KO partners with licensed e-money provider (Stripe Connect, Mangopay) rather than applying for own FCA license.

Context

Klash Coin (if 1:1 fiat-backed) constitutes e-money under UK Electronic Money Regulations 2011. KO must either:

  1. Register with FCA as e-money institution
  2. Partner with existing licensed provider

Rationale

  • Time to market: Partnering is significantly faster than FCA registration
  • Compliance burden: Provider handles AML/KYC, PCI DSS, reporting
  • Focus: KO can focus on product, not regulatory paperwork
  • Technical integration: Well-documented APIs (Stripe Connect, Mangopay)

Recommended Providers

Provider Strengths Pricing Suitability
Stripe Connect Market leader; excellent API; marketplace payouts 2.9% + 20p per transaction ✅ Best for Phase 1
Mangopay Europe-focused; e-wallet native 1.8% + 18c per transaction ✅ Lower fees
PayPal Payouts Ubiquitous; trusted Higher fees; clunky API ⚠️ Backup

Consequences

  • ✅ Launch-ready in weeks, not years
  • ✅ FCA compliance handled by provider
  • ✅ Proven, secure infrastructure
  • ⚠️ Per-transaction fees (1.8-2.9%) — factor into pricing
  • ⚠️ Dependent on provider (but Stripe/Mangopay are stable)

Related Decisions: DD-003 (Wallet Model), DD-010 (Cash-Out Flow)

DD-005: Authentication Strategy — JWT with Refresh Tokens

APPROVED | Date: 20 July 2026

Decision

Authentication uses JWT (JSON Web Tokens) with refresh tokens for session management.

Flow

  1. User logs in with email + password
  2. Backend returns access token (JWT, 1-hour expiry) + refresh token (7-day expiry, stored in DB)
  3. Frontend includes access token in Authorization: Bearer <token> header
  4. When access token expires, frontend requests new one using refresh token
  5. If refresh token invalid/expired, user must log in again

Rationale

  • Stateless: JWT contains user ID + role, no server-side session lookup
  • Secure: Short-lived access tokens limit damage if leaked
  • Revocable: Refresh tokens in DB can be revoked (logout/ban)
  • Industry standard: Used by Google, GitHub, Auth0

Alternatives Considered

Alternative Pros Cons Verdict
Session cookies Simple; revocable Requires server-side session store; harder to scale ❌ Less scalable
JWT only (no refresh) Simplest Long-lived tokens are security risk ❌ Fails NF05
JWT + Refresh Secure; scalable; revocable Slightly more complex ✅ Selected

Consequences

  • ✅ Satisfies NF05 (secure authentication)
  • ✅ Horizontal scaling (no shared session state)
  • ✅ Mobile app can use same auth system
  • ⚠️ Must implement token refresh logic in frontend
  • ⚠️ Must store refresh tokens securely (hashed in DB)

DD-006: Real-Time Architecture — WebSockets with Room-Based Pub/Sub

APPROVED | Date: 20 July 2026

Decision

Real-time events (chat, votes, klash state changes) use WebSockets (Socket.io) with room-based pub/sub.

Architecture

  1. Each Klash creates unique "room" (identified by klashId)
  2. When user joins klash, WebSocket client joins the room
  3. Backend broadcasts events to all clients in room (O(N) fan-out)
  4. Clients maintain optimistic UI updates with server reconciliation

Room Types

  • klash:{klashId} — all participants
  • user:{userId} — personal notifications
  • lobby:{genreId} — matchmaking queue

Rationale

  • Socket.io is mature, handles fallback to polling
  • Room-based limits broadcast scope
  • Sub-200ms latency achievable (satisfies NF02)

Alternatives Considered

Alternative Pros Cons Verdict
HTTP Long Polling Works everywhere High latency (1-2s); inefficient ❌ Fails NF02
Server-Sent Events (SSE) Simple; one-way No client→server; browser limit ❌ Not suitable for chat
WebSockets (Socket.io) Low latency; bidirectional; mature Requires persistent connections ✅ Selected

Consequences

  • ✅ Satisfies NF02 (≤200ms real-time event delivery)
  • ✅ Satisfies NF03 (10K concurrent users — scales with Redis adapter)
  • ✅ Excellent developer experience
  • ⚠️ Must handle connection drops gracefully
  • ⚠️ Scaling beyond 10K requires Redis pub/sub adapter

DD-009: Transaction Types as Single Entity

APPROVED | Date: 20 July 2026

Decision

All wallet transactions (top-up, gift, purchase, entry fee, winnings, cash-out) stored in single Transaction table with type discriminator.

Schema

CREATE TABLE transactions (
  id UUID PRIMARY KEY,
  type VARCHAR(50) NOT NULL,
  from_wallet_id UUID REFERENCES wallets(id),
  to_wallet_id UUID REFERENCES wallets(id),
  amount DECIMAL(10,2) NOT NULL,
  status VARCHAR(20) NOT NULL,
  metadata JSONB,
  created_at TIMESTAMP NOT NULL
);

Rationale

  • Single source of truth: All transactions in one table simplifies queries
  • ACID: Single table makes atomic constraints easier
  • Audit trail: Unified transaction log for regulatory reporting
  • Flexible: metadata JSONB allows transaction-specific data

Alternatives Considered

Alternative Pros Cons Verdict
Separate tables per type Clearer schema per type Fragmented audit trail; complex queries ❌ Over-normalized
Single table with discriminator Unified audit trail; simpler queries Nullable columns ✅ Selected

Consequences

  • ✅ Easy to generate full wallet history
  • ✅ Regulatory reporting simplified
  • ⚠️ Must enforce referential integrity via application logic

DD-010: Wallet Balance as Computed Field

APPROVED | Date: 20 July 2026

Decision

Wallet.balance is stored (denormalized) but recomputable from transactions.

Justification

  • Performance: Showing balance is most frequent query; computing SUM(transactions) every time is slow
  • Consistency: Balance updated atomically within same transaction that creates Transaction record
  • Auditability: Balance can be recomputed and compared to stored value (daily reconciliation)

Implementation

CREATE TABLE wallets (
  id UUID PRIMARY KEY,
  user_id UUID REFERENCES users(id),
  klash_id UUID REFERENCES klashes(id),
  owner_type VARCHAR(20) NOT NULL,
  balance DECIMAL(10,2) NOT NULL DEFAULT 0.00,
  currency VARCHAR(3) NOT NULL DEFAULT 'GBP',
  created_at TIMESTAMP NOT NULL
);

Consequences

  • ✅ O(1) balance lookup (satisfies NF01)
  • ⚠️ Must update balance atomically
  • ⚠️ Requires daily reconciliation job to detect balance drift
