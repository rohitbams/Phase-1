Epic Hierarchy & Build Order

Feature Organization & Implementation Sequence | 20 July 2026

Document Purpose

An Epic is a large body of work that breaks down into individual user stories. This document shows how KO's 12 epics are organized and the recommended build sequence for Phase 2 implementation.

Why Build Order Matters

You build epic by epic, not feature by feature. Some epics are foundational (User Accounts) — everything else depends on them. Others are peripheral (Music Social) — they can wait until the core platform is stable.

Key Principle: Build infrastructure first, then core game loop, then social features, then monetization extensions.

Recommended Build Sequence (Phase 2)

Phase 2A: Foundation (Weeks 1-4)

Order Epic Why Build First Delivers
1st Epic 1: User Accounts Every feature sits behind authentication. No accounts = no platform. Users table, JWT auth, tier system (RBAC)
2nd Epic 2: Music Library No music = no klash. Build storage + streaming before game logic. Track entity, S3 storage, CDN streaming, upload pipeline

Phase 2B: Core Game Loop (Weeks 5-10)

Order Epic Why Build Now Delivers
3rd Epic 3: Klashing This is the product. Build the core game loop before any extensions. Matchmaking, real-time game state (WebSockets), voting, results, points system
4th Epic 8: Wallet (Basic) Monetization is critical. Build top-up + basic wallet after core game works. Wallet entity, Stripe integration, transaction ledger, top-up flow

Phase 2C: Social Layer (Weeks 11-14)

Order Epic Why Build Now Delivers
5th Epic 5: Profile & Feed Users need identity and social proof. Profile aggregates all other data. Profile page, stats aggregation, news feed, follower system
6th Epic 11: Forums Discovery layer — users need to find active klashes to spectate. Live klash browser, genre-based forums, spectate flow
7th Epic 7: Playlists Organization tool — helps users prepare for klashes. Playlist CRUD, klash playlist loading, sharing

Phase 2D: Extensions (Weeks 15+)

Order Epic Status Notes
8th Epic 6: Messaging 🟡 Important but not blocking Standard feature, well-understood pattern (WebSockets)
9th Epic 4: Tournaments 🟡 Start with 1 format (Swiss or Elimination) Complex bracket logic — build incrementally
10th Epic 10: Nudge Play ⚠️ BLOCKED — mechanic undefined Cannot design until Lincoln defines what "nudge" does (see Q2.2)
11th Epic 9: Go Live 🟢 Advanced — requires WebRTC Video streaming on top of audio streaming — significant complexity
12th Epic 12: Music Social 🟢 Nice-to-have Music snippet messaging, recommendation engine — defer to later phase

Note: The above sequence is a recommendation, and can prioritised differently based on business goals.

Epic 1: User Account Management

FOUNDATION MUST BUILD 1ST

Engineering Overview

The account system is the foundation of everything. Every other feature in KO sits behind authentication. Before a user can klash, listen to music, send a coin, or follow anyone — they need an account.

Key Technical Components

  • Users table — Core entity that all other tables foreign-key to
  • Authentication strategy — JWT tokens (recommended) or OAuth provider
  • Tier system (RBAC) — Klasher / Independent / Super permissions
  • Password hashing — bcrypt (cost factor 12)
  • Privacy settings — Profile visibility, blocking

Dependencies

None — This is the first epic built. Everything else depends on it.

Architecture Impact

The Klasher tier system gates feature access across the entire app. A poor implementation here creates technical debt that ripples through every other epic.

Source: KO_Requirements_Document.md — Epic 1

Epic 2: Music Library & Song Selection

FOUNDATION MUST BUILD 2ND

Engineering Overview

The music library is the content layer of KO. Without music, there is no Klash. This epic directly intersects with Domain Requirement D01 (music licensing) — the library cannot go live without appropriate rights clearance.

Key Technical Components

  • Object storage (S3) — Music files are large binaries, not stored in PostgreSQL
  • CDN layer — CloudFront or Cloudflare for streaming performance
  • Chunked streaming — Audio must stream progressively, not download fully first
  • Upload pipeline — Format validation, transcoding, indexing
  • Genre entity — Controlled vocabulary referenced by Track and Klash

Dependencies

  • Epic 1 (User Accounts) — Track.artist_user_id foreign key
  • Domain Requirement D01 — Music licensing confirmed

Critical Decision

Music library source at launch: Independent Klasher uploads only (recommended) vs licensed major-label catalogue (requires PPL/PRS licenses). See Q1.2.

Source: KO_Requirements_Document.md — Epic 2

Epic 3: Klashing — Core Game

CORE LOOP MUST BUILD 3RD

Engineering Overview

This is the heart of KO. The Klash game is what differentiates this platform from everything else. It is also the most technically complex epic in Phase 1 to design and Phase 2 to build.

Core Technical Challenges

  • Real-time synchronization — WebSockets (Socket.io) for state sync across all participants
  • State machine — 10-state flow (MATCHMAKING → READY → COUNTDOWN → PLAYING_1 → DECISION_WINDOW → PLAYING_2 → VOTING → CALCULATING → RESULT → COMPLETED)
  • Audio synchronization — All users must hear snippets simultaneously (sub-200ms latency requirement)
  • Voting system — Atomic vote recording, one vote per user, tally calculation
  • Result determination — Primary: audience vote; Fallback: algorithm (see Q2.1)

Sub-Features

  • Matchmaking — Pairing users by genre, waiting queue
  • Game Setup — Track selection, snippet duration (30/60/90s)
  • Klash chat — Temporary group chat during session
  • Points system — Win = +X points, Loss = -Y points (values TBD, see Q2.4)

Dependencies

  • Epic 1 (Accounts) — User authentication, tier permissions
  • Epic 2 (Music) — Track library, streaming infrastructure

Architecture Impact

This epic drives your real-time architecture decisions: WebSocket library (Socket.io vs Pusher), room-based pub/sub, Redis for multi-server WebSocket scaling, state persistence strategy.

Source: KO_Requirements_Document.md — Epic 3

Epic 8: Klash Coin & Wallet

MONETIZATION BLOCKING: C01

Engineering Overview

This is the most legally sensitive and financially complex epic in the entire project. Read Domain Requirements D02 and D03 before approaching any wallet implementation decision.

Critical Decision (BLOCKING)

Fiat-backed vs Blockchain? See Conflict C01. This must be resolved before wallet can be designed.

Working assumption: 1:1 fiat-backed internal ledger with Stripe/Mangopay partnership (NOT blockchain).

Key Technical Components (Fiat Approach)

  • Double-entry ledger — Transaction table with from_wallet_id and to_wallet_id
  • Stripe Connect integration — Card processing, KYC/AML, FCA compliance
  • ACID transactions — PostgreSQL ensures zero unbalanced movements (NF06)
  • Transaction types — Single table, discriminated: TOP_UP, GIFT, MUSIC_PURCHASE, KLASH_ENTRY, KLASH_WINNINGS, HOST_FEE, CASH_OUT
  • Wallet.balance — Stored (for performance) but recomputable (for audit)
  • Daily reconciliation job — Compare stored balance vs SUM(transactions)

Dependencies

  • Epic 1 (Accounts) — Wallet belongs to User
  • Epic 3 (Klashing) — Klash winnings, entry fees, pot escrow
  • Domain Requirement D02 — FCA e-money compliance confirmed

Strong Recommendation

Do not build a custom wallet from scratch. Use a regulated third-party provider (Stripe Connect, Mangopay) that is already FCA-authorised. This offloads: card processing, PCI DSS compliance, KYC/AML, e-money regulation, payouts, fraud prevention.

Source: KO_Requirements_Document.md — Epic 8

Epic 4: Tournament Formats

EXTENSION

Engineering Overview

Tournament formats are structured competition systems that sit on top of the core Klash game. They organize multiple Klash matches into a structured event with a defined champion.

Formats

Format Complexity Recommendation
Single Elimination Low ✅ Build first — common, simple bracket logic
Swiss System Medium ✅ Build second — good for competitive balance
Round Robin High ⚠️ Impractical at scale (N² matches)
Free-For-All Low ✅ Simplest — just group klash

Technical Components

  • Bracket/pairing engine — Match participants based on format rules
  • Round management — Track which round is active
  • Result aggregation — Calculate standings across multiple matches
  • Leaderboard — Real-time standings display

Dependencies

  • Epic 3 (Klashing) — Tournament is a container for multiple Klashes

Recommendation

Build one format in Phase 2 (Single Elimination or Swiss), validate with users, then add others incrementally in Phase 3.

Source: KO_Requirements_Document.md — Epic 4

Epic 10: Nudge Play

BLOCKED TACTICAL

Status

⚠️ CANNOT DESIGN OR BUILD — The game mechanic (what "nudging" actually does) is undefined.

See Q2.2 — this is the most critical open item in the requirements document.

What We Know

  • Available in 60s and 90s klashes only
  • Timing window: Can be used 10s into klash, NOT in last 10s
  • FFA variant allows up to 3 nudge uses per participant
  • Costs Klash Coins (amount TBD)

What We Don't Know (Blocking)

What does nudge actually DO to the game?

Possible mechanics to explore with Lincoln:

  • Briefly interrupt opponent's audio playback (skip/mute)
  • Temporarily hide vote count from opponent
  • Force opponent's decision window to close early
  • Allow nudger to play own snippet mid-game
  • Visual distraction on opponent's screen

Dependencies

  • Epic 3 (Klashing) — Nudge is a tactical move within klash
  • Epic 8 (Wallet) — Nudge costs coins
  • Lincoln decision on mechanic — BLOCKING

Source: KO_Requirements_Document.md — Epic 10

Other Epics (Summary)

Epic 5: User Profile & Social Feed

SOCIAL

Overview: Public identity aggregating stats from all other epics. Most join-heavy query in system (Users, Klashes, Followers, Playlists, Wallet). News feed requires push mechanism (WebSockets or polling).

Dependencies: Epic 1, 3, 7, 8

Epic 6: Messaging

SOCIAL

Overview: Real-time private messaging between users. Requires WebSockets for instant delivery. Message storage at scale is a cost consideration.

Dependencies: Epic 1

Note: Distinct from Klash chat (F39) which is temporary group chat within game session.

Epic 7: Playlist Management

ORGANIZATION

Overview: Organizational tool for music. Klash Playlist is a game asset loaded into klash session. Many-to-many relationship: Track ↔ Playlist with ordering.

Dependencies: Epic 1, 2

Epic 9: Go Live

ADVANCED

Overview: Video/audio streaming during klash. Requires WebRTC, media server (SFU), low-latency delivery. Go Live Showcase for Independent Klashers is standalone performance (Twitch-like).

Dependencies: Epic 1, 3

Complexity: Video streaming on top of existing audio streaming — significant technical addition.

Epic 11: Forums & Discovery

DISCOVERY

Overview: Live klash browser — discovery layer for spectators. Genre-based forums, spectate flow. Technically interesting: F66 (put klash on hold) requires serializing complete game state.

Dependencies: Epic 3

Business rule: All live klashes must conclude within 24 hours (automated enforcement required).

Epic 12: Music Social

PERIPHERAL

Overview: Music snippet messaging (send 30s snippet instead of text). Recommendation engine (collaborative filtering or content-based). Most algorithmically complex feature — ML-level problem.

Dependencies: Epic 1, 2, 6

Recommendation: Start with rule-based system ("top tracks in genres you've klashed in"), evolve to ML later.
